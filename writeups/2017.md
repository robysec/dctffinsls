## State agency (web)
Source: [state_agency](https://github.com/p4-team/ctf/tree/master/2017-11-09-defcamp-final/state_agency)

**Setup.** A site for reporting vulnerabilities where almost nothing works except reading two existing reports. The report id appears in the URL's hostname (`<id>.state-agency…`), and a bad id produces an SQL error.

**Finding the injection point.** The id doesn't come from the visible URL parameters; it comes from the **`Host` header**. Changing the host changes the id used in the query, so the `Host` header is injectable.

**The obstacles.** An internal WAF blacklisted most useful SQL (including `information_schema`), and the injection point sits *after* a condition that restricts results to public reports.

**How it was beaten.**
1. `UNION SELECT` was not blacklisted, so `…') union select 1,2,3,4,5 -- a` echoed values and showed which columns are printed.
2. With `information_schema` blocked, the table name was found with MySQL's **`PROCEDURE ANALYSE()`**, which reports the database, table and column names (`agency.articles`, column `content`).
3. Reading the flag column directly triggered "Private data exfiltration attempt blocked", because the WAF scans responses for the flag. Wrapping the column in **`to_base64(...)`** hides it from that check; decode locally.

**Takeaway.** Blacklists miss alternatives (`PROCEDURE ANALYSE`), and an output filter that looks for a literal string is defeated by re-encoding.

## Fedora shop (web)
Source: [fedora_shop](https://github.com/p4-team/ctf/tree/master/2017-11-09-defcamp-final/fedora_shop)

**Setup.** A hat shop. After ordering, an order's status changes from "Pending approval" to "Shipped" shortly after, which strongly suggests an admin bot reviewing orders: a classic stored-XSS setup.

**Vulnerability.** The *Telephone* field of the order isn't sanitised, so JavaScript runs in the admin's browser.

**Two constraints and the workarounds.**
1. *Field length limits.* The payload won't fit in one field. Fix: put a tiny loader in the vulnerable field that `eval`s the text of another table cell on the page (the "other information" field),
   and chain a second `eval` from the address field. The real script is split across fields.
2. *The admin is firewalled and can't call out to an attacker server.* Fix: exfiltrate through the shop itself. The cart is stored server-side and keyed by the `PHPSESSID` cookie, and the admin *can* reach the shop on localhost.
   The injected script fetches `/admin.php`, then makes the admin's browser POST an "add to cart" request using **the attacker's own session id**, with the stolen page text as the `quantity`
   (the server never checked that quantity was a number). The attacker then opens their own cart and reads the data.

**Takeaway.** When egress is blocked, find a feature that stores attacker-controllable data you can read back. Also, "quantity must be numeric" is validation worth checking.

## Hack tac toe (web/crypto)
Source: [hack_tac_toe](https://github.com/p4-team/ctf/tree/master/2017-11-09-defcamp-final/hack_tac_toe)

**Setup.** Two-player tic-tac-toe in the browser. A cookie `Encrypted_Game_Session` changes as you play.

**Reasoning.**
1. Changing one letter of the player name changes only about one byte of the cookie, so this is a **stream cipher** (or XOR with a keystream), and the keystream does not change between requests.
2. Chosen-plaintext trick: set the player name to 100 `a` characters, compare the old and new cookies, find where they start to differ (byte 112), and XOR that span with the known `a`s to recover keystream bytes.
3. Using that keystream on the original cookie reveals a PHP-serialised array (`a:5:{s:4:"flag";…`, with the flag as the first element), but no obvious exploit.
4. The recovered keystream **repeats every 16 bytes**. With a 16-byte repeating key the whole cookie decrypts, and the serialised array contains the flag.

**Takeaway.** Always inspect the recovered keystream. A short period means you hold the whole key; reusing a keystream across messages gives chosen-plaintext decryption.

## Caesar's favourite song (misc/crypto/stego)
Source: [favourite_song](https://github.com/p4-team/ctf/tree/master/2017-11-09-defcamp-final/favourite_song)

**Setup.** An MP3 ("kill the Gauls"), and the flag format `DCTFXXXDCTF`.

**Solution.**
1. Transcribe the audio to notes (MusicXML) with free software. Octave matters: notes from a different octave were marked (lowercase) to keep them apart.
2. Combine consecutive notes in **pairs**. The pairs at the start and the end of the sequence were identical, matching the `DCTF` prefix and suffix, which is the crib.
3. From `DCTF` the team derived that a pair means *(first note value × 16) + (second note value)*, a byte split into two nibbles, with `A→4, G→3, B→5, c→6`.
4. Those values are not random: they fit the **D major scale**. Applying the full scale decodes the middle of the flag.

**Takeaway.** Use the known flag format as a crib to find the mapping, then look for a real-world structure (here, a musical scale) that explains it.

## Audio captcha (misc/ppc)
Source: [audio_captcha](https://github.com/p4-team/ctf/tree/master/2017-11-09-defcamp-final/audio_captcha)

**Setup.** Solve many distorted voice captchas in a row without a failure. Speech-to-text services didn't work.

**Insight.** The audio is WAV, i.e. a raw sample stream, and although it sounds distorted the captcha is **assembled from the same pre-recorded clips every time**, with no random distortion.

**Solution.**
1. Download a batch of captchas and label some by hand.
2. Cut each into its 10 symbol segments and store a chunk of bytes per symbol as a pattern.
3. For a new captcha, split it into 10 pieces and match each against the patterns. If a piece matches more than one pattern, skip this captcha and fetch another; if every piece matches exactly one, submit.
4. Repeat until the required streak is reached.

**Takeaway.** Don't use ML where exact matching works; skipping ambiguous samples makes a simple solver reliable.

## Adversarial (misc/ppc)
Source: [adversarial](https://github.com/p4-team/ctf/tree/master/2017-11-09-defcamp-final/adversarial)

**Setup.** The server holds a 100×1000 matrix of random values in (−1, 1) and picks one row. You send a 100-value vector with entries in (−1, 1). It computes the dot product `z` with the row and passes it through `1 / (1 + e^(−z))`; you win if `1 − that` is below 0.001.

**Solution.** The sigmoid approaches 1 as `z` grows, so you want the biggest possible dot product. Each term is largest when your component has the same sign as the row's component and magnitude 1, so send **`+1` where the row value is positive and `−1` where it is negative**. (An "adversarial example" in the plainest form.)

## Infinity (web/network, 400 pts) — other team
Source: winw / 0x90r00t, [blog post](https://0x90r00t.com/2017/11/14/dctf-finals-2017-web-400-infinity-write-up/) and [CTFtime writeup 8018](https://ctftime.org/writeup/8018) (search excerpts only; page not opened).

**Setup.** A single scannable host (the writeup reconstructs it as `10.2.63.250`); the goal was to get "past a firewall".

**What the scans showed.** An intense nmap scan found three open ports — 8008, 8010 (an SSL/HTTP proxy fingerprinted as a *FortiGate Web Filtering Service*) and 8020. 8008 redirected to 8010; 8020 behaved as a proxy that blocked navigation when set in a browser.

**The trick — port 0.** Organiser hints pushed everyone to "check every port". A default nmap run does **not** scan port 0, and the real service was listening there. Port 0 is normally un-addressable in most tooling, which is exactly why it was missed. (The excerpt cut off before the final flag retrieval; read the full post for the last step.)

**Takeaway.** Default scans have blind spots. When a hint insists there is "one more port" and you have already enumerated the obvious ones, consider the edges of the range (port 0, high UDP, etc.) and tools that can actually address them.

## Security CCTV (misc, 374 pts) — other teams
Sources: [CTFtime writeup 10412](https://ctftime.org/writeup/10412) and a [NorthernCoalition gist](https://gist.github.com/Becojo/37f7f47b27b532f0353a7235f42b73c6) (search excerpts only).

**Setup.** A camera feed whose frame hides a QR code that is rotated, skewed and split.

**Solution.** Image processing: pull a frame, correct rotation/skew, boost contrast, map the QR's four corners onto a clean square (a ~200×200 image), re-assemble the mirrored/split pieces, and composite onto a plain background so a reader can decode it. Balsn reported doing the reassembly by hand in GIMP/Photoshop rather than scripting it.

**Takeaway.** For distorted-QR tasks, a perspective transform from the four detected corners plus a contrast pass is usually enough; scripting it (OpenCV `getPerspectiveTransform`) beats manual pixel-pushing under time pressure.

## Silent (reverse) — other team
Source: bookgin / Balsn, [D-CTF 2017 Final post](https://bookgin.tw/2017/11/24/d-ctf-2017-final/) (search excerpt only). Balsn finished 9th/11.

**Approach.** Conceptually simple: a byte-by-byte oracle that leaks the flag one character at a time. The real time-sink was infrastructure — the organisers forwarded the service through `socat`, which **mangled the payload** before it reached the challenge, so exploits that worked locally failed remotely until the team accounted for the rewriting. More than one team complained about it.

**Takeaway.** When a remote-only exploit misbehaves but the local one works, suspect the transport (proxies, `socat`, line-ending or encoding rewrites) before doubting your logic.
