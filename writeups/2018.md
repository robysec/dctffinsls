Event: [CTFtime event 698](https://ctftime.org/event/698).

## Authenticator (pwn category, really reverse + crypto) — 2 solves
Source: p4 team's [`2018-11-8-defcamp-finals/authenticator`](https://github.com/p4-team/ctf/tree/master/2018-11-8-defcamp-finals/authenticator), **read in full**.
A second, independent writeup ([jiancanxuepiao](https://jiancanxuepiao.github.io/2018/11/08/defcamp-finals/)) was only seen as a search excerpt and agrees on AES-128-CTR.
p4's author notes the task was mis-categorised as pwn, which probably explains the low solve count.

**What the service does** (pseudocode recovered from the binary):
1. Wait for the string `HELLO`.
2. Print two random 16-byte values from `/dev/urandom`, call them `bytes1` and `bytes2`.
3. Read your 16-byte answer. If `crypto(bytes2, your_input, key) == bytes1`, print the flag encrypted with the same function.

**Reverse-engineering the crypto.** The binary is C++ and uses boost's SHA-1 (identified by a path string) and Crypto++ for the cipher. Vtable type-info strings
(`CryptoPP::CTR_ModePolicy`, `CryptoPP::Rijndael::Base`) reveal it is **AES-128 in CTR mode**. Breaking on the function showed its arguments: the first is the counter (random per run),
the fourth is the key (constant bytes). To confirm, the author reimplemented it in Python and got the same output as the binary for the same inputs.

**Solving it.** CTR mode is symmetric: encrypting and decrypting are the same XOR with the keystream. To make the check pass, send `AES-CTR(key, ctr=bytes2)` applied to `bytes1`.
Then the encrypted flag the server returns decrypts with the same key and counter.

**Remaining problem — the key.** With ASLR off the key was constant, but with ASLR on **its first byte changed every run** (the other 15 bytes stayed the same; the author checked several Linux systems).
Solution: brute-force the first key byte, 256 values, reconnecting each time and stopping when the decrypted output contains `DCTF`.

**Takeaway.** A task labelled "pwn" can be a pure reversing/crypto problem. Strings and RTTI/vtable names in C++ binaries often identify the library and algorithm in minutes, and a
small unknown (one byte) can simply be brute-forced online.

## Scribbles (web) — other teams
Sources (both **read in full** from GitHub mirrors): [Balsn's writeup](https://balsn.tw/ctf_writeup/20181108-defcampctffinal/) (bookgin et al.) and [kaibro / DoubleSigma](https://github.com/w181496/CTF/tree/master/dctf2018-final/Scribbles). Flag value and verbatim final payloads are deliberately left out below.

**The service** (single PHP file). A POST with no `action` builds a string `payload = "data=$data&name=$name"` where `$name = uniqid()`, signs it with `hash_hmac('md5', payload, FLAG)`, and curls it back to *itself* at `?action=log` on `127.0.0.1`. The `action=log` branch verifies the HMAC, re-parses the payload, then writes a file to `files/<time()>.<last 20 chars of name>` with your `data` as contents. If `base64_decode(data)` is non-empty it appends an extension (`jpg`/`php`/`raw`) and uses the decoded bytes; a final guard rejects contents longer than 37 bytes.

**Why you can't just forge it.** The HMAC key is the flag, and the signed request is made server-side to localhost, so you can neither forge the signature nor read it (SSRF goes to localhost, the signature never comes back). The whole attack has to go *through* the legitimate self-request.

**The chain.**
1. **Parameter injection into the signed string.** Your `data` is concatenated unescaped into `data=$data&name=$name`. Injecting `...&name=<your name>` plus a trailing NUL lets you override `$name`. curl truncates the request body at the NUL byte, so the original `uniqid()` tail is dropped and you control the filename. Both `uniqid()` and `time()` are predictable, so you know where the file lands.
2. **Forcing a `.php` name past the extension logic.** The extension is only appended when `base64_decode(contents)` is non-empty. PHP's `base64_decode` returns an empty string when the input contains **no valid base64 characters at all**, so a webshell built entirely from non-alphanumeric bytes decodes to empty — the `.php` you set via the NUL trick survives unmodified.
3. **A ≤37-byte non-alphanumeric webshell.** Using `<?=` (short-echo works where `<?` is off), backticks for shell execution, and XOR/NOT of punctuation strings to synthesise the identifier `_GET` without letters, the team built a 37-byte shell that runs `$_GET[...]`. kaibro's variant uses a NOT trick to synthesise `cat` and dump `config.php` directly. (An operator-precedence bug in the ternary `ext` selector is a red herring that makes the "intended" `.php` route not work — hence the base64-empty trick.)

**Takeaways.** Unescaped concatenation into a parsed key/value string is injectable just like SQL; NUL truncation differs between layers (curl vs PHP) and that gap is exploitable; `base64_decode` silently dropping invalid chars is a classic filter bypass; and alphanumeric-free webshells are a known art (see leavesongs' posts linked from the writeup).

## TicketCore (web, SQL injection) — other team
Source: [Balsn's writeup](https://balsn.tw/ctf_writeup/20181108-defcampctffinal/) (bookgin, sasdf, sces60107), **read in full**.

**Setup.** A ticket API `/printable-ticket/<id>`. Fuzzing shows `'` triggers a 500 and `'='` behaves like a true condition — a classic string-context SQL injection. Target: read the `code` of ticket id 1 (a private VIP ticket), which is the flag.

**The WAF and the bypasses.**
- `and`/`or`/`if` are blocked → use `&&` and `||` for boolean-blind logic.
- The literal `DCTF` and `0x...` hex literals are blocked → represent the comparison string as a **binary literal** (`0b...`) instead, and extract the flag character-by-character with range comparisons (`code > 0b... && code < 0b...`).
- Alternative path: every MySQL string function is filtered **except `to_base64`**. Comparing `to_base64(code)` works, but because the base64 of the flag itself contains the filtered substring `if`, you base64-encode **twice** and compare that. MySQL comparisons are case-insensitive, so case is lost — recoverable here only because the flag body is lowercase hex.

**Takeaways.** Boolean-blind SQLi survives aggressive keyword blacklists via `&&`/`||`; numeric/binary literals dodge string-literal filters; and when string functions are filtered, the one survivor (`to_base64`) plus double-encoding can still smuggle your comparison past the WAF. Watch for case-insensitive comparisons destroying information.
