## Simple notes (web, 50 pts, 16 solves)
Source: [simple-notes](https://github.com/p4-team/ctf/tree/master/2019-11-07-defcamp-finals/simple-notes)

**Setup.** A small note app: each user has a sandbox, can upload "small files", and can list them.

**The bug.** The listing request carries a `cmd` parameter containing a **base64-encoded shell command** (the "standard" one is `ls -la *`). That is remote command execution, though a strict whitelist of
characters limits what you can type, and at the minimum you keep the characters of `ls -la *`.

**Intended trick (noticed, then dropped).** Uploads can be one byte long, so a directory full of one-character file names could be made to expand through `*` into an arbitrary command. It was visible to other teams and fiddly.

**What p4 did.** Use shell **wildcards** instead of typing names:
1. `ls -la /*/*` to find where the flag lives (`/var/www/html/flag/flag.php`).
2. Reach that file with a glob like `/*a*/www/**/**/*.p*`.
3. `cat` was unreachable with the alphabet, so find any binary that prints a file and can be globbed. `awk 4 <file>` does: the program `4` is a constant that is always true, and awk's default action for a true pattern is to print the line, so it prints the whole file. It was reached as `/*s*/*/aw* 4 <glob>`.

**Takeaway.** With a character whitelist, globs let you name files and binaries you can't spell. Look for alternatives to the usual `cat`.

## Crypto (136 pts, 12 solves)
Source: [crypto](https://github.com/p4-team/ctf/tree/master/2019-11-07-defcamp-finals/crypto)

**Setup.** Encryption code and a ciphertext. The key is parsed into three integers `a, b, c`, 8 hex characters each. For each byte: `keystream = (b & 0xff) ^ (c & 0xff)`, then `out = ((byte − (a & 0xff)) ^ keystream) & 0xff`,
after which `a` rotates right and `b`, `c` rotate left.

**Weakness.** Per the writeup, `b` and `c` are rotated left as **64-bit** values although they were built from small (8-bit) values, so they quickly become 0 as far as the keystream is concerned (the code only uses their low byte). After that only the subtraction with the rotating `a` is left. I did not re-run this.

**Approach.** Instead of inverting by hand, translate the cipher into Z3 bit-vector constraints (only add/subtract, AND, XOR and rotations are involved), add the constraint that each plaintext byte is printable,
and the known prefix `Congrats! Flag is: `. At first the prefix wasn't known, so the team asked Z3 to enumerate solutions and filtered by charset until the prefix appeared.

**Last wrinkle.** The decrypted tail came out slightly wrong. The first 40 hex characters of the ciphertext are the SHA-1 of the whole plaintext, so the remaining three unknown characters were brute-forced
(128³ combinations) until the hash matched. The plaintext is the "Congrats…" line with the flag.

**Takeaway.** Use a solver for a cipher built only from simple bit operations, and use any embedded checksum to fix ambiguity.

## Treasure map (forensics/OSINT, 136 pts, 12 solves)
Source: [treasure-map](https://github.com/p4-team/ctf/tree/master/2019-11-07-defcamp-finals/treasure-map)

**Setup.** A PDF full of geographic place names. Analysing streams and fonts led nowhere.

**Idea.** The names at the very start of the content are repeated at the very end, which looks like a `DCTF` prefix and suffix around the real flag. Then, by chance, the team noticed that one place, *Kruglyy Prud* (a pond),
looks like the letter **D** on a map. The other places also look like letters or digits, so the flag is read off the shapes of the named features. (The writeup doesn't give the full list.)

**Takeaway.** When a puzzle repeats its own start at its end, treat that as a prefix/suffix crib; and the "data" may be visual.

## Lucky (web, 304 pts, 5 solves)
Source: [lucky](https://github.com/p4-team/ctf/tree/master/2019-11-07-defcamp-finals/lucky)

**Setup.** A service with a closed router: only `index.php` and `404.php` exist, and everything else redirects to 404.

**Clue.** Requesting `/404.php` with a raw **HTTP/1.0** request gives two different kinds of reply: sometimes labelled HTTP/1.0 and sometimes HTTP/1.1. The team first assumed a proxy or load balancer split and tried keep-alive tricks.

**What it really was.** The server **broadcasts the flag as a bit stream** using the protocol version: `1.0` means 0, `1.1` means 1. The value changed about every three seconds while a request was sent about once a second.

**Complications.**
- The service kept crashing or stalling (a 500 error). After each restart it replayed a different, random portion of the bit stream.
- Samples were sometimes missed, so each bit appeared as a run of about three equal samples that sometimes came out as two or four. A heuristic normalised run lengths to multiples of three.
- The starting bit might be mid-character, so all 8 offsets were tried and bytes were scored on whether they looked like flag characters.

**Reassembly.** It took about **three hours** to collect enough overlapping fragments, which were then lined up like a jigsaw to get the full 64-hex-character flag.

**Takeaway.** Side channels can be as odd as protocol-version labels. Log everything, collect fragments, and align by overlap.
