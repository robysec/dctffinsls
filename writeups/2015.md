## web 200 — SQL injection through EXIF
Source: [web200](https://github.com/p4-team/ctf/tree/master/2015-11-20-dctffinals/web200)

**Setup.** An image uploader reads the file's EXIF data and uses the `Software` field to look up and show other pictures made with the same software.
The goal is to read a `flag` table.

**Vulnerability.** The `Software` value goes straight into a `WHERE` clause, so a crafted EXIF `Software` string is an SQL injection.
It is awkward: the injected text is capped at about 50 characters, `UNION` can't be used, and the queried table has zero rows, so there is nothing to echo back.

**Attempt 1 — timing oracle.** Use `BENCHMARK()` (no `SLEEP`) so a wrong guess burns CPU. Each guess tested a sliding window with `LIKE '%window%'`,
because `SUBSTRING` didn't fit in 50 characters. It worked but each wrong guess spawned a very long job (up to ~40 per character), the team crashed the server five times,
recovered about two thirds of the flag, and the organizers then blocked `BENCHMARK`.

**Attempt 2 — error oracle (what worked).** Make the query *valid or invalid* depending on a condition: `rlike(if(mid((select*from flag),i,1)='c','',1))`.
A true guess keeps the query valid; a false one produces an error the page shows differently. That is one yes/no answer per request, looped over
position × character set, using a script that rewrites the EXIF field, uploads the file, and checks the response.

**Takeaways.** When time-based and `UNION` routes are closed, any visible difference (valid vs error) is a 1-bit oracle. Don't hammer a shared service with heavy queries.

## crypto 100 — "Morse c'est"
Source: [crypto100](https://github.com/p4-team/ctf/tree/master/2015-11-20-dctffinals/crypto100)

**Setup.** A captured conversation encoded in Morse, but the "dumb protocol" removed all the spaces. The flag is an MD5 (`dctf{md5}`).

**Problem.** Without separators, Morse is ambiguous, so one dot/dash string has a huge number of valid readings. The team generated close to 20 million candidate decodings
(restricted to digits and `A–F`, hoping for an MD5) and tried dictionary solvers, without success.

**Resolution.** About eleven of the twenty-four hours in, the organizers admitted it was unsolvable as published and re-released it with invisible Unicode characters
(zero-width spaces) as the separators. Then it was trivial and every team solved it; the decoded text is a long English passage about computers.
The writeup does not spell out how the passage maps to the final MD5 flag.

**Takeaway.** Information that was destroyed can't be recovered; look for hidden characters before brute-forcing, and expect the occasional broken task.

## crypto 300 — leaking key bits through the high bit
Source: [crypto300](https://github.com/p4-team/ctf/tree/master/2015-11-20-dctffinals/crypto300)

**Setup.** A JavaScript cipher and one ciphertext; decrypt it.

**Analysis.** Each output byte is `input ⊕ table ⊕ key`, where the table holds values 0–127 and the key bytes are ASCII. If the key is shorter than the text it is
*extended* by repeatedly bit-shifting it left and appending the result.

**The leak.** The input is ASCII and the table is 0–127, so neither can set bit 7. Only the shifted key material can. So the high bit of each ciphertext byte tells you
that key byte's high bit. Because each extension shifts the key left, across a long enough message you see every bit of every key byte
(the first extension exposes the 2nd-highest bit of the original key, and so on). This works when the key is at least 8× shorter than the message.

**Finding the key length.** The first ciphertext byte whose high bit is set marks where key extension began, which is an upper bound on key length.
For each candidate length from 2 up to that bound, collect every Nth high bit and pack them into bytes. At length 21 this gives `weplayctfoutofpassion`
(21 characters, checked). Feeding it to the original decrypt routine yields a congratulations message containing the flag.

**Takeaway.** A cipher that lets structure from the key reach a bit the other inputs can't touch hands out the key.

## crypto 400 — a keyless cipher is linear
Source: [crypto400](https://github.com/p4-team/ctf/tree/master/2015-11-20-dctffinals/crypto400)

**Setup.** Three known plaintext/ciphertext pairs and a fourth ciphertext that holds the flag. The hint says the cipher uses no key.

**Observations.**
1. The high bit of every ciphertext byte follows the same pattern in all four messages (one of them inverted).
2. XOR-ing each ciphertext byte with its neighbour (`ct[i] ^ ct[i+1]`) gives identical values for two messages wherever their plaintexts match, and differs exactly where they differ.
   Concretely, two plaintexts differing at one position by `0x20 ^ 0x27 = 0x07` produced neighbour-XORs that also differ by `0x07` (checked).

**Conclusion.** For every position, `plain_a[i] ^ plain_b[i] == xorct_a[i] ^ xorct_b[i]`. The "cipher" is XOR-linear with a fixed, key-independent mask,
so one known pair unlocks every other message: `plain_new[i] = xorct_new[i] ^ xorct_known[i] ^ plain_known[i]`. Applying that to the fourth ciphertext printed the flag message.
(The team's first version brute-forced each byte; it worked immediately.)

**Takeaway.** A keyless transform is just an encoding. Differences between ciphertexts that mirror differences between plaintexts is the fingerprint of linearity.

## reverse 200 — Time is not your friend
Source: [re_200_time_is_not_your_friend](https://github.com/p4-team/ctf/tree/master/2015-11-20-dctffinals/re_200_time_is_not_your_friend)

**Setup.** An ELF with no input. It loops from 2 upward and, for numbers it "likes", prints "Well done". The number it stops on is the flag.

**What the code does.** It checks each number for primality, counts the primes seen, and stops when the count reaches about 49,000,000 *and* the prime's digits sum to 41.
The `sleep()` calls and `clock()` timing tests are anti-shortcut padding: the "real" path is the one taken when the program runs slowly.

**Solution.**
1. Take the slow-path behaviour as the intended one and strip the sleeps and timing branches.
2. Replace the naive primality loop with a fast trial-division test.
3. Don't count from 2: start near the right prime (the writeup starts the scan at 961,748,862 with the counter set to 49,000,000), then run until a prime has digit sum 41.
4. Result `961749023`. Re-checked: it is prime and its digits sum to 41.

**Takeaway.** Remove time-based obfuscation, identify the underlying math (prime count, digit sum) and skip the work instead of waiting for it.

## reverse 300 — Try harder
Source: [re_300_tryharder](https://github.com/p4-team/ctf/tree/master/2015-11-20-dctffinals/re_300_tryharder)

**Setup.** An ELF that takes the flag as `argv[1]` and says whether it is right.

**Visible checks.** Length at most 100, exactly 37 characters, prefix `DCTF{` with an alphanumeric next, and the 32 characters after the prefix are split into eight 4-character
groups, each matching a small regular expression (for example `^9[0-2]6[4-7]`). Passing all of these prints "Well done", but the site still rejected the flag.

**The trap.** The program keeps running after `main` returns: a **destructor** performs one more check. It sums a per-character formula over the characters after the prefix
and reduces it modulo 74,431,661 (the compiler's multiply-and-shift division trick makes this look scarier than it is); the result must equal 25,830,287.

**Solution.** Don't reverse it. Generate every candidate allowed by the regular expressions and brute-force the destructor check in C++. The surviving flag is not unique.

**Takeaway.** Always look at constructors, destructors and `atexit`/fini code. If a "success" message doesn't convince the server, there is another check.
